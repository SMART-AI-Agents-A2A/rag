# RAG

[Português](README.BR.md)

Retrieval-Augmented Generation (RAG) service used in the project to query technical documents and produce answers grounded in documentary evidence. This repository contains the HTTP service, command-line interface, text corpus, source PDFs, execution configuration, and automated tests.

## RAG type and processing

The implementation is a **modular RAG pipeline with dense vector retrieval and two-stage retrieval (*retrieve-and-rerank*)**. Query planning supports decomposition into multiple searches. Planning, reranking, sufficiency assessment, and generation are configurable modules; vector search is the central retrieval stage.

| Property | Implementation |
| --- | --- |
| Retrieval unit | Text chunk associated with a document and section |
| Representation | Dense vector generated by `baai/bge-m3`, with 1,024 dimensions in the supplied configuration |
| First stage | Cosine similarity search in Qdrant |
| Second stage | Candidate reordering with `cohere/rerank-v3.5`, enabled by default |
| Planning | One or more subqueries; at most four per request |
| Constraints | Exact metadata filters for language, crop, region, topic, and document type |
| Selection | Score threshold, candidate deduplication, and per-document chunk limit |
| Generation | Context assembled from selected evidence, with citation identifiers |
| Sufficiency assessment | Optional module; disabled by default |
| Architectural scope | Documentary pipeline; no lexical/BM25 search, knowledge graph, or autonomous tool loop |

| Stage | Operation | Output |
| --- | --- | --- |
| 1. Loading | Validates YAML metadata and requires `review_status: approved` | Documents eligible for indexing |
| 2. Chunking | Splits by Markdown headings and overlapping text windows | Chunks with section paths, SHA-256 hashes, and UUIDv5 identifiers |
| 3. Indexing | Generates embedding batches and synchronizes Qdrant | Persistent vector index |
| 4. Planning | Decomposes the question and restricts filters to the corpus vocabulary | Retrieval plan |
| 5. Retrieval | Embeds subqueries and searches for candidates | Passages ordered by similarity |
| 6. Reranking | Reassesses the relationship between the question and passages | Relevance ordering |
| 7. Selection | Applies score, quantity, and document diversity limits | Evidence identified as `rag:<uuid>` |
| 8. Answering | Generates text from the passages and checks cited identifiers | Answer, evidence, coverage assessment, and metadata |

If planning fails, the original question is used. If reranking fails, vector scores are retained; they are also used when no reranked result exceeds its threshold and eligible vector candidates exist. Generation failures retain the evidence and return `answer: null`. Citation validation requires at least one retrieved identifier and rejects unknown `rag:` identifiers; it does not provide semantic verification of every claim.

## Models and parameters

Models are accessed through OpenRouter at `https://openrouter.ai/api/v1/embeddings`, `/rerank`, and `/chat/completions`. The identifiers below are service configuration values. Remote stages require an API key with access to the corresponding models.

| Stage | Provider | Model identifier | Temperature | `top_p` | Default state |
| --- | --- | --- | --- | --- | --- |
| Embeddings | OpenRouter | `baai/bge-m3` | Not applicable | Not applicable | Required for indexing and querying |
| Planning | OpenRouter | `meta-llama/llama-3.1-8b-instruct` | `0.5` | `1.0` | Enabled |
| Reranking | OpenRouter | `cohere/rerank-v3.5` | Not applicable | Not applicable | Enabled |
| Generation | OpenRouter | `deepseek/deepseek-v4-flash` | `0.7` | `1.0` | Enabled; maximum 900 output tokens |
| Sufficiency | OpenRouter | `openai/gpt-4o-mini` | `0.5` | `1.0` | Disabled |

Temperature and `top_p` are sent in text generation requests. The embedding and reranking endpoints receive task-specific parameters without text sampling settings. These values are operational configurations, not experimentally optimized results. Provider interfaces are described in the [OpenRouter RAG documentation](https://openrouter.ai/docs/guides/evaluate-and-optimize/rag).

| Retrieval parameter | Default | Interpretation |
| --- | --- | --- |
| Target chunk size | `1000` characters | Includes the document and section prefix; this is not a token count |
| Overlap | `150` characters | Reuses context between windows within a section |
| Embedding batch | `32` texts | Maximum per ingestion request |
| `top_k` / maximum requested | `3` / `8` | Desired evidence count and configured maximum |
| Global evidence limit | `6` | Also caps returned evidence when `top_k=8` |
| Chunks per document | `2` | Limits concentration on a single source |
| Candidates | `20` | Target count distributed across subqueries |
| Subqueries | Up to `4` | Limit applied to the question plan |
| Vector threshold | `0.30` | Cutoff applied to cosine similarity |
| Reranking threshold | `0.30` | Cutoff applied to the reranker score |

The two scores use different scales. Responses identify the applied scale in `metadata.score_kind` and the applied threshold in `metadata.score_threshold`.

## Docker and Docker Compose

The [Dockerfile](Dockerfile) provides `runtime` and `test` targets. The image includes the installed package, Markdown corpus, and PDFs. [docker-compose.yml](docker-compose.yml) configures the API, Qdrant, ingestion, and test execution.

```bash
docker compose build rag-api rag-ingest
docker compose up -d --wait qdrant
docker compose --profile maintenance run --rm rag-ingest
docker compose up -d --wait rag-api
curl --fail http://127.0.0.1:8080/health
```

Ingestion uses the OpenRouter key from `.env`. The API can start before ingestion to expose the inventory and configuration; queries return `not_available` while the collection does not exist.

| Service | Host address | Compose network address | Persistence and role |
| --- | --- | --- | --- |
| `rag-api` | `127.0.0.1:8080` | `rag-api:8080` | API; read-only `./documents` mount |
| `qdrant` HTTP | `127.0.0.1:6333` | `qdrant:6333` | Index stored in the `qdrant-storage` volume |
| `qdrant` gRPC | Not published | `qdrant:6334` | Available in the image; the service uses HTTP |
| `rag-ingest` | No port | Connects to `qdrant:6333` | Ingestion process in the `maintenance` profile |
| `rag-tests` | No fixed port | Connects to `qdrant:6333` | PyTest in the `test` profile; test server uses an ephemeral port |
| OpenRouter | Outbound HTTPS on port `443` | `openrouter.ai:443` | Remote model service |

If host ports are occupied, change `RAG_API_PORT` and `RAG_QDRANT_PORT` in `.env`; internal addresses remain as listed. For local execution, also adjust `RAG_QDRANT_URL` when changing Qdrant's published port.

```bash
docker compose ps
docker compose logs --tail=100 rag-api
docker compose down
```

`docker compose down` stops services and preserves the index volume.

## Local execution and CLI

Run commands from the repository root:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.lock -e '.[dev]'
docker compose up -d --wait qdrant
.venv/bin/rag documents
.venv/bin/rag config
.venv/bin/rag ingest
.venv/bin/rag serve
```

| Command | Operation |
| --- | --- |
| `rag documents` | Lists documents and metadata |
| `rag config` | Displays public settings without credentials |
| `rag ingest` | Indexes new or changed documents and removes deleted documents |
| `rag ingest --reset` | Recreates the collection and all vectors |
| `rag query "question"` | Retrieves evidence and generates an answer according to configuration |
| `rag query --no-answer "question"` | Retrieves evidence without answer generation |
| `rag serve` | Starts the HTTP server |
| `python -m rag` | Module entry point equivalent to the `rag` command |

Ingestion does not recompute embeddings for documents whose hashes are unchanged. Updates write new chunks before removing obsolete identifiers.

## HTTP API

| Method | Path | Input and output |
| --- | --- | --- |
| `GET` | `/health` | `200` when Qdrant and the corpus are accessible; `503` when degraded; collection existence is reported separately |
| `GET` | `/v1/config` | Public model, limit, and chunking configuration |
| `GET` | `/v1/documents` | Corpus inventory with metadata and SHA-256 hashes |
| `POST` | `/v1/ingest` | Body `{"reset": false}`; requires a Bearer token when configured |
| `POST` | `/v1/query` | Question, filters, and options; returns evidence, plan, assessment, and an optional answer |
| `GET` | `/docs` | Interactive API interface |
| `GET` | `/openapi.json` | OpenAPI specification |

```bash
curl --fail http://127.0.0.1:8080/v1/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"Which documents discuss irrigation management?","top_k":3,"generate_answer":true,"filters":{"language":"en"}}'
```

| Query field | Type | Behavior |
| --- | --- | --- |
| `query` | Text, 2 to 4,000 characters | Required; whitespace is normalized |
| `top_k` | Optional integer, 1 to 20 | Subject to `RAG_MAX_TOP_K` and the global limit |
| `generate_answer` | Optional boolean | Overrides the global generation setting for this request |
| `filters` | Optional object | `language`, `crop`, `region`, `topic`, `document_type`; exact inventory values |

Explicit filters override planned filters. Omitting the language filter allows cross-language retrieval.

| Response status | Meaning |
| --- | --- |
| `ok` | The sufficiency judge confirmed complete coverage |
| `partial` | Evidence exists, but complete coverage has not been confirmed |
| `collection_gap` | No candidate exceeded the selection threshold |
| `not_available` | The collection does not yet exist |
| `source_error` | Index access or embedding retrieval failed |

With the judge disabled, responses containing evidence remain `partial`, with `retrieval_sufficiency_not_validated`. Documentary status is returned in the JSON body, including when the HTTP status is `200`.

Run the tests with real Qdrant through Compose, without model credentials:

```bash
docker compose --profile test run --build --rm rag-tests
```

Or use local PyTest:

```bash
docker compose up -d --wait qdrant
.venv/bin/python -m pytest --qdrant-url=http://127.0.0.1:6333
```

Server tests use temporary `pytest_<uuid>` collections and remove them afterward. Local tests control model request transport; they do not measure remote model semantic quality or performance. External tests are marked `skipped` unless their options are supplied.

To test the provider with the `.env` key and make billable requests to the configured models:

```bash
.venv/bin/python -m pytest --live-provider -m live
```

This test uses two test documents and in-memory Qdrant. It requires evidence, a cited answer, and success of enabled stages; it fails if credentials, models, or their endpoints are unavailable.
